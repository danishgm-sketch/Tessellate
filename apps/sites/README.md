# Tessellate Sites deployment adapter

The application remains Astro with React islands and the canonical Workbench,
composer, schemas, resource catalogue, renderer and standalone exporter. Astro
produces the human-facing static artifact. An isolated asset Worker adds response
headers because the original Sites static deployment did not enforce `_headers`.
The Hono API, Better Auth, D1 and R2 architecture is unchanged.

From the repository root:

```sh
pnpm install --frozen-lockfile
pnpm build
```

The workspace build orders `@tessellate/sites` after `@tessellate/site`, copies the
Astro output into an ignored adapter asset directory and emits `dist/server` plus
`dist/client` using the Cloudflare Vite plugin. The small Worker streams `ASSETS`
responses and enforces CSP, nosniff, framing, referrer and permissions headers.
During packaging, it hashes inline scripts and style elements across the 716
public HTML pages. The app-shell policy allows only those exact script/style
hashes; the separate style-attribute allowance remains because existing React
and Astro output uses inline style attributes.
Worker code does not host the canonical account or inference queue API. The Sites Vite
hosting plugin is vendored from the official starter with its MIT licence.

Preview with `pnpm --filter @tessellate/sites preview` (port 4323). On Windows,
run the long-lived preview in a PTY and stop it before rebuilding so that the
Worker asset cache does not hold build output files open. Local startup uses
`CLOUDFLARE_CF_FETCH_ENABLED=false` and `WRANGLER_SEND_METRICS=false` when testing.
The compatibility date matches the supplied Sites starter: 2026-05-15. The pinned
starter Wrangler runtime cannot emulate a newer compatibility date locally.

## Compatibility differences

- Source `.openai/hosting.json` omits the static field so Sites deploys the asset
  Worker. Public HTML and React modules are still generated by Astro.
- The Worker preserves the non-CSP header intent and replaces the broad static
  app-shell CSP with build-certified inline script/style hashes. Preview CSP
  blocks arbitrary network connections, nested frames and external assets. Its
  only `connect-src` exception is the same-origin immutable `/_astro/` asset
  path, needed for the browser's fetch-based stylesheet preload in opaque frames.
- Preview frames use opaque `sandbox="allow-scripts"` iframes, and the preview
  response repeats that restriction with CSP `sandbox allow-scripts` so direct
  navigation also cannot access Site storage or submit forms. The preview CSP
  explicitly sets `form-action 'none'`; public pages restrict form submission
  to their own origin. Public compiled modules have
  wildcard CORS so those frames can import vetted resource code; no API or
  credential-bearing endpoint gets wildcard CORS.
- The public app-shell policy permits only its documented same-origin and
  production API/preview origins. Development loopback origins are excluded
  from both the Sites Worker policy and the static `_headers` fallback.
- The deployed Explore audit found that the browser fetches a compiled stylesheet
  while loading resource modules in opaque preview frames. The path-scoped asset
  exception allows only public compiled `/_astro/` files; APIs, arbitrary same-
  origin routes, external hosts, credentials, and nested frames remain blocked.
- The static stylesheet compatibility alias remains for previously published
  URLs; current canonical page sources import the stylesheet through Astro.
- Guest projects, collections and checkpoints use existing browser persistence.
  Provider credentials are not persisted. Core work needs no provider key.
- Authentication, shared cloud project storage and community publishing still
  require the canonical API and its credentials. CLI and stdio MCP packages are
  distributable programs; this deployment does not pretend to host those processes.

No D1/R2 binding, new database, paid SaaS, hosted inference or always-on server was
introduced. Sites billing is not exposed by the connector; no exact Sites tariff
is asserted. This adapter adds no paid infrastructure outside Sites and preserves
the repository's £20 maximum principle.

## Latest main publication (2026-10-13)

The application source is taken from main commit
`22f2961d10c76e9f4ff263965c9bd894f8ea3a9c`, including the expanded resource
registry and multi-target exporter. Earlier audit application changes have not
been overlaid on that newer source. Only this hosting adapter and the single
stylesheet build option are retained.

The CPU Tree-GNN daemon cannot execute inside a Cloudflare Worker. The
owner-operated Docker backend is documented in `../laptop-backend/README.md`.
The Site adapter now supports a server-only authenticated HTTPS backend proxy,
with an explicit offline response until its permanent connection is configured.
Host control endpoints are never forwarded. Recognized deterministic commands
remain local when offline; unsupported prompts are unavailable without changing
the project. No hosted D1/R2 binding is provisioned by this extension.

This publication updates the latest project for review. The prior V7 audit does
not certify the newer main implementation; deployment smoke results are recorded
in `LATEST_DEPLOYMENT.md`.

### Native asset routing difference

The live Sites runtime bypassed the Worker for matching static assets even when `run_worker_first` was configured. The adapter therefore packages assets under `__tessellate_asset_payloads` and renames HTML payloads to binary extensions. Public requests are translated by the Worker, which sets the original content type and security headers. No application source or public route is rewritten. This difference was discovered during the deployed audit, not inferred from localhost.
